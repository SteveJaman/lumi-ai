The core difference between Lumi and Neuro is not intelligence.
It is ARCHITECTURE. Neuro runs continuously, has internal state,
makes its own decisions, and acts without being prompted.

Lumi waits. Neuro lives.

Every item below closes that gap. Ordered by dependency —
later items assume earlier ones are done.

  Notable delta since last update (2026-09-29):
    - PHASE 8.1 SHIPPED (protocol definition).
      sdk/protocol.py is the single source of truth for message
      shapes. Client and server builders live there. Message format
      matches Neuro: {"command": str, "game": str, "data": {...}}.
      Commands are namespaced ("actions/register", "action/result").
      Action payloads use JSON-Schema parameters, compatible with
      both Ollama's tool interface and OpenAI's function calling.

    - PHASE 8.2 SHIPPED (server module).
      sdk/server.py exposes SDKServer, a Module that binds to
      127.0.0.1:5056, authenticates clients with a token stored at
      memories/sdk_token.txt (0600 on POSIX), and manages the
      action registry. Public methods used by the prompter:
        get_action_schemas()    → tool schemas in Ollama format
        get_context_injections() → free-text from connected clients
        find_action(tool_name)  → resolve "sdk__<name>"
        invoke_action_blocking(name, args) → run a client action
        broadcast_lumi_message(text) → fan out speech_finished
      Accepts both new {"command": ...} and legacy {"type": ...}
      message shapes for backwards compatibility.

    - PHASE 8.3 SHIPPED (prompter integration).
      modules/prompter.py gained three surgical edits:
        1. run_agent_turn now appends SDK schemas to the tool list
           and prints "[SDK] N action(s) available" on every turn.
        2. _dispatch_tool_call resolves "sdk__<name>" tool calls and
           routes them through SDKServer.invoke_action_blocking().
           Honours requires_confirm and dangerous capabilities with
           a y/n gate before running.
        3. run() broadcasts each assistant reply to connected SDK
           clients via sdk.broadcast_lumi_message().

    - PHASE 8.4 SHIPPED (client library).
      sdk/client.py provides LumiClient, an importable base class.
      Subclass it, override setup(), register actions with handlers,
      call .run(). The library handles the websocket, auth
      handshake, ping/pong, reconnection with backoff, action
      registration, invocation dispatch, and result formatting.
      Handlers may return (bool, str), a bare bool, a string, or a
      dict — all four shapes are normalized.

    - PHASE 8.5 SHIPPED (fake-client test harness).
      sdk/examples/system_stats.py is a runnable reference client
      that registers CPU/memory/disk stats and a desktop
      notification. Doubles as a fake-client harness.

    - PHASE 8.8 PARTIAL (capability tiers).
      Action specs carry capabilities=["read"|"write"|"dangerous"]
      and requires_confirm=bool. The server enforces the y/n gate
      at dispatch time. read actions auto-approve, write actions
      log, dangerous actions always prompt. Refining the policy
      (per-client trust levels, capability allowlists) is future
      work.

    - NEW FILES THIS SESSION:
      sdk/__init__.py          — public exports
      sdk/errors.py            — SDKError, AuthError, ProtocolError,
                                 ActionError, ClientDisconnected
      sdk/protocol.py          — wire format + builders

    - FILES MODIFIED THIS SESSION:

    - DESIGN LESSON (documented for future plugin developers).
      Small-model tool selection routes by token overlap. Three
      plugin actions failed to fire before one worked:
        open_notepad         → lost to run_in_terminal
        get_time_in(city)    → lost to web_search's timezone handler
        read_clipboard       → lost to run_command clip
        screenshot_*         → succeeded (no competitor)
      Rule: a plugin action needs a capability that no built-in
      tool and no shell command covers. If either exists, the model
      will route to it, because built-ins appear in the schema list
      from turn 1 and shell commands share query vocabulary.

  PHASE 9 — SECURITY HARDENING                        NOT STARTED
================================================================

Goal: Close attack surfaces across the entire stack. Threat
model is local, not remote: malicious content Lumi reads,
malicious SDK plugin, accidental self-modification, other
local processes reaching the web client or SDK.

  In scope:   prompt injection via file/web/memory/SDK content;
              SDK hijacking; self-modification; API key
              exposure; command escalation; network exposure;
              CSRF and DNS-rebinding; session hijacking.
  Out of scope: kernel compromise, hardware attacks, physical
              access, supply-chain attacks on Ollama.
